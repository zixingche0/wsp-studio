# 编辑 DSL 设计说明

这份文档解释**为什么**编辑计划长现在这样。每条设计决策都对应一次实测或一次踩坑。

---

## 1. 为什么切哪个维度必须显式写

官方 exp8 的编辑是：

```
W = down_proj.weight   shape [1024, 3584]
W[:, selected_64_cols] -= alpha * u ⊗ v
```

注意：
- `[1024, 3584]` 是 `[hidden, intermediate]`
- 改的是 **3584 那一维的 64 列**
- **1024 行全覆盖**

如果把它理解成"输出维度的 64 列"（也就是 `axis=0`），会完全改错地方。

不同模型家族的 `down_proj` 方向甚至可能相反（有些是 `[intermediate, hidden]`）。所以 schema 里 `axis` 是**必填**，不给默认值。

---

## 2. 为什么有 `rank1_subtract`

一开始我以为 `direction_ablation`（投影移除）就够了。抓了官方张量做比对后发现：

- 官方差分矩阵 `σ₂/σ₁ ≈ 0.001` → **严格 rank-1**
- 每列改动强度几乎相同（std/mean ≈ 0.6）→ 是同一个 `u⊗v` 作用在 64 列上

但 `project_out` 是"减掉切片**自身**在 d 上的投影"，是自适应的，减多少取决于切片本身。要**精确复现**一个已知的外部方向，必须是 `W -= α·u⊗v`。

所以两个算子都要：
- `project_out` — 诊断式的，"我不知道确切方向，先试试"
- `rank1_subtract` — 复现式的，"我有确切方向，精确减掉"

---

## 3. 为什么 `index.kind: "list"` 是主力

实测官方选的 64 列是：`0, 2, 11, 25, 34, 35, 38, 39, ... 2066, 2738, 3003`

- **不连续**
- **不是按列范数选的**（被选列范数的平均百分位是 0.63，最差的排到 3570/3584）
- 也不是按绝对值均值选的

它们是 Astra 通过分析激活、找到"写循环方向的那 64 个通道"选出来的。

所以我们提供的 `index.kind`：

| kind | 用途 |
|---|---|
| `list` | **主力**。规划器/用户给出确切索引 |
| `top_norm` | 兜底。没有更好信号时，按范数取 top-N |
| `range` | 只用于测试和明确知道范围的情况 |
| `all` | 整个张量（几乎必超 1% 预算） |

---

## 4. 为什么 `relative_change` 是"差异范数/原范数"

官方 manifest 里 `relative_change = 0.1064`。一开始我算的是 `(‖new‖-‖old‖)/‖old‖`，结果是 `-0.000001`——差了五个数量级。

正确口径：

```
relative_change = ‖new - old‖ / ‖old‖
```

这个数字回答的是"改了多少"，不是"范数变了多少"。这才是审计时想看的东西。

---

## 5. 为什么 bf16 必须走位操作

官方改动 131,072 个元素，但 `changed_entries` 只有 130,188。差的 884 个是**被改动后 bf16 舍入回原值**的元素。

如果我们用浮点做、再比较浮点，会得到 131,072，与官方对不上，也无法做逐 bit 校验。

所以：
- 存的是 `uint16` 位模式
- `bf16_bits()` 做 round-to-nearest-even
- 比较用 `!=` 直接比位

`tests/test_official_reference.py` 里验证了能用这个方式重建出和官方 sha256 一致的张量。

## 6. 为什么 1% 上限是硬编码的

wsp-kit 把 `MAX_EDIT_FRACTION = 0.01` 写在代码里，注释是"the 1% cap is enforced here, in code, not just in the docs"。

理由：
- 超过 1% 的编辑基本等于微调，不是"精准编辑"
- 且不可解释、不可回滚地精细
- 用户点"应用"时不知道自己在做什么

我们的做法：`ops.check_budget()` 在每次编辑后检查，超了**抛异常**，整个计划的这条编辑失败，`dry_run` 结果里明确显示。

---

## 7. 为什么门控的 `primary` 是单个字符串

因为门控要回答的是**一个二值问题**："这次编辑该不该留？"

如果有多个主指标，就会出现"数学涨了 5 分、指令遵循跌了 8 分，算不算通过"这种无法自动判定的情况。

所以：
- `primary`：**唯一**判定提升的指标
- `guards`：其余不许退化的指标

其余指标都放在 `guards` 里，任一退化超限就否决。

---

## 8. 为什么 planner 的 prompt 里有负面知识

`wsp/llm/prompts.py` 的 `PLANNER_SYSTEM` 里写了：

> 1. 你无法从权重读出领域语义（10 次盲测 0 命中）
> 2. 你无法预测一次编辑的具体效果（相关系数 0.06~0.09）
> 3. 编辑只能移除障碍，不能新增能力
> 4. 多数编辑会被门控拒绝

这不是自我贬低，是**抑制幻觉**。LLM 天生倾向于给出自信的、看起来合理的编辑计划。不告诉它这些，它会编出"把 layer 12 的 gate_proj 缩放 1.3 倍可以提升推理能力"这种计划，然后被门控拒绝，浪费一次运行。

写上之后，它在证据不足时更愿意返回 noop。

---

## 9. 为什么探测要记录采样配置

OpenWSP 的对照实验证明：**关掉 thinking，Qwen3.5-0.8B 的 MATH-500 从 7.2% 直接跳到 46.8%**，撞上限率从 93.2% 降到 0.6%。

这个影响（+40 分）**远大于**任何一次权重编辑（官方那次是 +40 分，但那是精心设计的）。

所以探测摘要里必须有 `sampling`：`temperature / top_p / max_tokens / thinking`。否则测出来的"故障"可能只是解码配置造成的，改权重是南辕北辙。

我们的建议流程：如果探测发现循环，先试 `decoding_sweep`（换采样配置），确认确实是权重问题再改。

## 10. 未做的事（明确列出）

- **方向来源**：`direction_source` 目前支持 `explicit` / `random` / `svd_top1`。**没有**实现论文里的"从激活差估计方向"——那需要控制探针 prompt 并抓中间层激活，是 P2 的事。
- **注意力/线性注意力的编辑**：只验证了 `mlp.down_proj`。Qwen3.5 有 hybrid linear attention，那部分的结构不同，没测。
- **多模态**：Qwen3.5-0.8B 带 vision tower，我们只编辑语言模型部分，vision 完全没碰。
- **KL 散度 guard**：`evaluate_gate_with_ppl` 留了接口，但没有实现从 logprobs 算 KL。
